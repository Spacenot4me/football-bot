# Полный контекст CUEFA Football Bot

Срез реализации: **2026-11-11**; структура исходной локальной базы изучена 25.10.2026.
Краткий вход для нового агента: [../AGENTS.md](../AGENTS.md).
Документ основан на всех исходных Python-файлах, SQL-скриптах, тестах,
конфигурации сборки и структуре локальной базы. Значения `.env` и строки
пользовательских данных не включены. Структура локальной базы — наблюдение,
она не гарантирована в другом развёртывании.

## Архитектура и жизненный цикл

```text
Telegram Bot API ←→ main.py / Application.run_polling()
                        │
                        ├─ команды и CallbackQueryHandler
                        │    ├─ users / bans / matches
                        │    ├─ register_funcs / remove_funcs
                        │    ├─ utils (вывод, история, права)
                        │    ├─ draft_funcs (капитаны, драфт, сообщения и права)
                        │    └─ pidor ──→ Mistral API
                        │
                        ├─ JobQueue (APScheduler, в памяти)
                        │    ├─ jobs_funcs.start (каждые 7 дней)
                        │    └─ register_funcs.check_for_confimation (через 4 часа)
                        │
                        └─ operations/* ──→ sqlite3 ──→ DATABASE_PATH
```

`main.py` импортирует обработчики, читает `TG_TOKEN`, создаёт `Application`,
регистрирует обработчики, вызывает `initiate()` и запускает polling.
`operations/common.py` читает `DATABASE_PATH` один раз при импорте.
`pidor.py` также при импорте читает ключ и создаёт `Mistral(API_KEY)`.
Основные таблицы регистрации приложение при старте не создаёт. Таблицы драфта
лениво создаются при обращении к `operations/team_drafts.py`.
`operations/registration_safety.py` также лениво создаёт три добавочные таблицы
из `migrations/add_registration_safety.sql`, без перестройки существующих таблиц.

Обработчики зарегистрированы в одной группе. Конкретные команды идут раньше
общего `filters.COMMAND → unknown_command`; неизвестная команда только логируется.
После `CallbackQueryHandler` стоит обработчик личных текстов, начинающихся с `@`
(с допустимыми ведущими пробелами), затем перехватчик неизвестных команд.
`handle_error()` записывает traceback в лог, не отвечает пользователю.
Единой настройки `logging.basicConfig()` в приложении нет.

Недельные задачи восстанавливаются из `Chats`, кроме чатов в `Paused_Registrations`;
задача называется Telegram ID чата. Пауза сохраняется после перезапуска.
Таймеры подтверждения и `context.user_data`/`chat_data` не сохраняются между
перезапусками. Пропущенные за время простоя недельные запуски отдельно не догоняются.
Недельные задачи — календарные cron-задачи через `JobQueue.run_daily` с одним
днём недели и явным `Europe/Prague`. Общий helper
`jobs_funcs.schedule_weekly_registration()` используется и настройкой чата,
и `main.initiate()`: местное время сохраняется при переходах лето/зима.
PTB считает дни с воскресенья, поэтому helper переводит индексы из Monday-based
словаря `date_utils.WEEKDAYS`. `coalesce=True` и `max_instances=1` не допускают
пачку накопленных запусков и одновременное выполнение одной недельной задачи.

Ручной `/start_registration` и недельный `start()` используют общий
`jobs_funcs._open_registration()`. `operations.matches.create_match_if_missing()`
в транзакции `BEGIN IMMEDIATE` проверяет пару `(Chats.id, Matches.datetime)` и
создаёт матч только при отсутствии неотменённого матча. Поэтому досрочное открытие, повторная команда,
рестарт и одновременные запуски не создают новый матч или сообщение регистрации
на то же игровое время. При повторе состав и драфт не меняются; по расписанию
повтор пропускается молча, команда отвечает, что запись уже открыта, и предлагает
`/show_registration_message`. Проверка использует все матчи чата, а не только
последнюю строку. Новый матч на следующую неделю открывается как обычно и закрывает
драфт предыдущего. Ранее созданные дубликаты не изменяются.
Отменённый матч можно явно открыть заново командой `/start_registration` на то же
игровое время, с новым ID. Недельная задача отменённый матч повторно не открывает.
Матч сохраняется до сетевых вызовов; если отправка сообщения не удалась, показать
сохранённую регистрацию можно через `/show_registration_message`.

`date_utils.BOT_TIMEZONE` — единый часовой пояс календаря и текущего времени;
`get_current_time()` не зависит от часового пояса ОС. `get_next_weekday()` вычисляет
целевую календарную дату и локализует её заново, поэтому будущий матч после
перевода часов сразу сохраняется с правильным смещением. `get_hours_until_match()`
считает реальную длительность между aware-datetime: через весенний переход сутки
могут составлять 23 часа, через осенний — 25. Для отсутствующего весеннего 02:30
принято выполнение в 03:30, повторный осенний 02:30 используется второй раз,
в стандартном времени; поведение проверено на триггерах закреплённого APScheduler.
`/get_jobs` выводит следующее выполнение в Prague со смещением.

Для перехода со старых интервалов достаточно обновить и перезапустить бот:
задачи восстанавливаются из существующих настроек `Chats`. Матчи, регистрации,
драфты и схема базы этой правкой не переписываются. Четырёхчасовые подтверждения
приглашений остаются `run_once` с длительностью в секундах; их восстановление
после рестарта по-прежнему не реализовано.

## Модель данных

`operations/common.py`: `connect_db()` устанавливает `sqlite3.Row`;
`fetch_query()` возвращает `list[dict]`, `fetch_one_query()` — `dict | None`,
`execute_query()` возвращает `cursor.lastrowid`, не число затронутых строк.
Общие запросы, подтверждение и удаление приглашения явно закрывают соединения
через `contextlib.closing`. Изменения драфта используют отдельные транзакции
с `BEGIN IMMEDIATE`, чтобы два одновременных подтверждения не сбросили его дважды.
`PRAGMA foreign_keys=ON`, WAL и единый механизм повторов при блокировках не заданы.

| Таблица | Значимые столбцы | Связи и использование |
| --- | --- | --- |
| `Users` | `user_id` PK, `nickname` UNIQUE в локальной базе, `name` | Глобальный реестр пользователей всех чатов; username без `@` |
| `Chats` | `id` PK, `chat_id`, `name`, `game_time`, `game_week_day`, `reg_time`, `reg_week_day` | `id` — внутренний ключ, `chat_id` — Telegram ID; дни на английском, время `HH:MM` |
| `Matches` | `match_id` PK, `chat_id`, `datetime`, `amount_per_person`, `created_at` | `chat_id` указывает на `Chats.id`; при создании цена 130 |
| `Match_Registration` | `registration_id` PK, `match_id`, `user_id`, `registered_by_id`, `is_plus`, `confirmed`, `priority`, `registered_at` | Запись игрока и её автор; подтверждение не отделено от общей очереди |
| `Bans` | `ban_id` PK, `user_id`, `until` | Баны глобальные для пользователя, без привязки к чату |
| `Random_Selections` | `selection_id` PK AUTOINCREMENT, `user_id`, `chat_id`, `selected_at` | Здесь `chat_id` — Telegram ID; таблица создаётся лениво командой выбора/статистики |
| `Players_Notifications` | `notification_id` PK, `chat_id`, `user_id` | Историческая подсистема; её `operations/user_notifications.py` не вызывается основными сценариями |
| `Team_Drafts` | `draft_id`, `match_id`, nullable `captain_a_id/captain_b_id`, `captain_mode`, `candidate_user_ids`, `first_pick`, `status`, `revision`, `draft_pick_count`, `replacement_a/b`, `roster_snapshot`, `main_message_id` | Один действующий драфт на матч; режим, очередь, дефициты команд и снимок всей регистрации |
| `Team_Picks` | `pick_id`, `draft_id`, `user_id`, `team`, `kind`, `state`, `pick_number` | Обычный выбор или замена, активная/вышедшая запись; уникальность активного игрока в драфте |
| `Team_Draft_Messages` | `id`, `draft_id`, `tg_chat_id`, `message_id` | Учёт главного сообщения, запросов, уведомлений и команд для удаления |
| `Team_Draft_Restart_Requests` | `request_id`, `draft_id`, `requested_by_id`, `draft_revision`, `status` | Сохранённые подтверждения рестарта: `pending`, `confirmed`, `cancelled`, `stale` |
| `Team_Draft_Cancel_Requests` | `request_id`, `draft_id`, `requested_by_id`, `draft_revision`, `status` | Сохранённые подтверждения отмены с теми же статусами; новая таблица создаётся без изменения существующих драфтов |
| `Registration_Id_Sequence` | `singleton=1`, `last_id` | Постоянный верхний предел выданных ID регистрации; удаление записи не уменьшает счётчик |
| `Paused_Registrations` | `chat_id` PK | Здесь `chat_id` — внутренний `Chats.id`; недельное расписание приостановлено |
| `Cancelled_Matches` | `match_id` PK | Маркер отмены; матч и его регистрации сохраняются, но недоступны для действий и не входят в историю |

В локальной базе есть индексы `idx_random_selections_chat_user` и
`idx_random_selections_date`. Ленивая функция `create_random_selection_table()`
создаёт только таблицу; индексы определены в `migrations/add_pidor.sql`.

`created_at`, `registered_at`, `selected_at` обычно используют SQLite
`CURRENT_TIMESTAMP` (UTC без смещения). Игровое время и баны записываются
с часовым смещением, разбираются через `%Y-%m-%d %H:%M:%S%z` / `fromisoformat`.
Это разные представления времени; нельзя считать их одной согласованной системой.

Текущий матч выбирается по `MAX(match_id)` внутри чата. Если именно эта строка
помечена отменённой, возвращается None: предыдущий матч не становится текущим.
«Прошлый матч» — последний по `datetime DESC, match_id DESC`, исключая строку
с максимальным ID и отменённые матчи; проверка даты относительно текущего времени
по-прежнему не выполняется. История пяти матчей выбирает последние неотменённые
матчи с записями, включая текущий, а затем проверяет членство игроков в Telegram.
Все три выборки основного состава ограничены `MAX_PLAYERS` в порядке
`priority, registered_at, registration_id`. Используются LEFT JOIN с `Users`:
удалённый профиль не скрывает игрока или его гостей, вместо профиля выводятся
числовой ID и `Deleted account`. Такой же порядок и LEFT JOIN использует драфт.

## Капитаны и драфт команд

`draft_funcs.py` отвечает за Telegram и проверки ролей. `operations/team_drafts.py`
хранит состояние, сверяет регистрацию и выполняет переходы без сетевых вызовов.
`migrations/add_team_drafts.sql` запускается лениво через `ensure_draft_tables()`;
это самостоятельная идемпотентная схема новых таблиц, а не исправление старых миграций.

Администратор запускает `/captains` (алиас `/capitans`) или `/captains random`
для случайного выбора из основного состава. `/captains @a @b` задаёт капитанов,
`/captains random @a @b ...` ограничивает кандидатов. Имена проверяются в `Users`
без учёта регистра, дубликаты запрещены. Кандидаты могут ещё не записаться на матч:
сессия сохранит их ID и дождётся регистрации. Дата матча и общее число записавшихся
не блокируют запуск; нужен существующий текущий матч настроенного чата.

Состояния: `waiting_for_players`, `drafting`, `done`, `needs_replacement`, `cancelled`.
При 0 или 1 подходящем игроке обе ссылки капитанов равны NULL, сообщение уже создано
и закреплено. Когда доступны оба капитана, они назначаются одновременно.
Первые `MAX_PLAYERS` записей в порядке приоритетов — основной состав, включая
`confirmed=0`. Резерв не выбирается до продвижения в основной состав.

Капитаны выбирают строго по очереди; `first_pick` случаен при старте и рестарте.
`draft_pick_count` сохраняет число обычных выборов, поэтому выход игрока или
повышение его до капитана не меняют чётность очереди. Пики замены не продвигают
обычную очередь. Последний обычный свободный игрок может автоматически достаться
следующему капитану, если размеры команд позволяют это; таймеров нет.
При нечётном составе допустима разница в одного игрока. Новая регистрация после
`done` возвращает доступного игрока в пул без полного сброса команд.

Хуки в `register_funcs.py` и `remove_funcs.py` синхронизируют драфт после самозаписи,
приглашения, подтверждения и всех вариантов удаления, включая таймер.
Снимок регистрации хранится в SQLite и включает резерв, ID записи, приоритет,
подтверждение и отображаемые данные. Изменения снимка увеличивают `revision`.
Это также позволяет обнаружить изменения после простоя при следующем обновлении.

Уход выбранного игрока увеличивает дефицит его команды и переводит её в
`needs_replacement`; выбирать замену может только её капитан. Если замены нужны
обеим командам, каждый капитан добирает собственные вакансии. При уходе капитана
новый выбирается только из оставшихся активных игроков его команды. Его активный
пик удаляется, но счётчик обычной очереди сохраняется. Если своей команды больше
нет, драфт отменяется, а причина сообщается в беседе.

`Restart draft` видна во всех действующих состояниях. Доступ — админам/владельцу
беседы и действующим капитанам; в ожидании без капитанов — только админам.
Первое нажатие сохраняет запрос и показывает Confirm/Cancel в беседе, не меняя
пиков. Подтвердить/отменить может только инициатор; при подтверждении права
проверяются повторно. Изменение версии, старый матч, чужой или уже использованный
запрос не выполняют сброс. Подтверждение и сброс атомарны, остальные pending-запросы
становятся stale. Кнопки выбора также несут revision и отклоняются после изменений.

`Cancel draft` также видна во всех действующих состояниях и доступна админам и
капитанам. Она и `/cancel_draft` создают запрос отмены с `Confirm cancellation /
Keep draft` в беседе; до подтверждения команды, очередь и состояние сохраняются.
Подтверждает только инициатор, после повторной проверки роли и версии драфта.
Keep draft закрывает запрос без изменений команд. Отмена транзакционна и делает
все остальные ожидающие запросы отмены/рестарта недействительными. Тихое сообщение
подтверждения учитывается в `Team_Draft_Messages` и удаляется вместе с драфтом.

Основное сообщение редактируется после выбора и изменения состава. `/teams`
создаёт и закрепляет новое, затем удаляет прежнее; если удалить нельзя, бот
пытается отключить его кнопки. Закрепление имеет `disable_notification=False`.
Выходы, смена капитана и необходимость замены сообщаются в беседу с обычным
уведомлением; запросы рестарта и служебные ответы — с `True`. Ошибки Telegram
логируются, не откатывая состояние; при невозможности закрепить драфт продолжает
работать. Ошибка «сообщение не изменилось» не создаёт дубль, удалённое главное
сообщение восстанавливается на обновлении.

Подтверждённая `/cancel_draft` или кнопочная отмена инвалидирует запросы и удаляет
учтённые сообщения по возможности. При отмене матча, открытии следующего и `/stop`
драфт также закрывается. Невозможность удалить сообщение из-за прав/ограничений
Telegram не отменяет сохранённую отмену. Удалённый аккаунт или внешние изменения
приоритета обнаруживаются при следующей синхронизации, но отдельного фонового опроса
нет. Команда `/set_priority` вызывает синхронизацию сразу после сохранения приоритета.

`main.configure_command_menu()` вызывается через `Application.post_init` при
запуске polling: `set_my_commands` обновляет стандартное меню и меню групп.
В нём есть `/captains` с примерами `@a @b | random | random @a @b @c`, `/teams`,
`/cancel_draft` и `/draft_help`. Справка доступна всем и не создаёт сессию драфта.
Меню охватывает все 30 зарегистрированных команд, включая алиасы, административные
и старые пункты. `/register_another_from_chat` из игровой беседы открывает тот же
личный список, что Register +1; функция использует `update.effective_user`, поэтому
работает и для команды, и для callback. Текстовый `/confirm` ведёт в
`register_funcs.confirm_command()`: показывает инструкцию нажать Confirm в
конкретном личном приглашении. Без указания матча/приглашения произвольная запись
не подтверждается. Тест сверяет точное совпадение меню со всеми CommandHandler,
включая алиасы и отсутствие дубликатов. Сбой обновления меню логируется и не блокирует старт бота.

## Регистрация, приглашения и приоритет

`register_core()` проверяет предыдущую игру, текущую запись и время матча.
Уже неподтверждённую запись он подтверждает, существующую подтверждённую
не дублирует. Публичный путь приглашения отдельно отклоняет любое повторное
приглашение, чтобы приглашающий не мог подтвердить игрока за него.

Приоритет вычисляется при создании записи и автоматически не пересчитывается:

1. Активный бан → `4`.
2. Участие в основном составе прошлого матча и условие ранней записи → `1`.
3. До матча менее 26 часов → `3`.
4. Нет ни одной подтверждённой записи в истории пользователя → `3`.
5. Внешний гость (`is_plus`) → `3`.
6. Остальные → `2`.

Администратор игровой группы может изменить приоритет уже записанного игрока:
`/set_priority @username 1`. Имя команды латиницей, как требует Telegram.
Принимаются ровно два аргумента: username с `@` и целое значение от 1 до 4;
чем меньше значение, тем выше место в очереди. Обработчик `register_funcs.set_priority`
отклоняет личку/каналы, анонимный вызов, отсутствие прав, ненастроенный чат,
отсутствующий или уже начавшийся матч, неизвестного пользователя и игрока без записи.
Поиск в сохранённых `Users` без учёта регистра. Операция
`operations.match_registrations.set_match_registration_priority()` обновляет только
`priority` по внутреннему чату, текущему `match_id` и `user_id`; SQL повторно проверяет,
что матч всё ещё текущий. Время записи, подтверждение и приглашение сохраняются.
Баны и записи в других матчах/чатах не изменяются: это ручное переопределение на
один матч, в том числе для игрока с баном. Равные приоритеты по-прежнему упорядочены
по `registered_at`. После сохранения вызывается `draft_funcs.sync_registration()`:
переход между основой и резервом учитывается драфтом, старые версии кнопок становятся
недействительными. Ошибка доставки не откатывает приоритет. Ответ подтверждает новое
значение и предлагает Refresh на сообщении регистрации для обновления списка.

Фактическая проверка ранней записи: `(now - reg_time).total_seconds() / 7200 < PRIORITY_HOURS`.
При текущем `PRIORITY_HOURS=2` это примерно **4 часа**, хотя имя константы
подразумевает 2. `created_at` перед этим интерпретируется как локальное время Prague,
что добавляет отдельную погрешность. Не менять это молча как косметическую правку.

Ограничения приглашений считает `operations/match_registrations.create_match_registration()`
по паре `(registered_by_id, match_id)`: максимум одна запись каждого вида
«сам», «другой участник чата», «внешний гость». Участие самого приглашающего
не обязательно для приглашения. Проверки лимитов, существования обоих профилей,
текущего неотменённого матча, дубликата игрока, выделение ID и INSERT выполняются
в одной транзакции `BEGIN IMMEDIATE`. Уникального ограничения `(match_id, user_id)`
в старой таблице по-прежнему нет. `Registration_Id_Sequence` учитывает существующие
ID перед выдачей новых кнопок и никогда не уменьшает верхнюю границу после удаления.

Меню `Register ➕ 1️⃣` запоминает:

- `context.user_data['plus_one_prompt'] = {'chat_id': tg_chat_id, 'match_id': ...}`;
- `context.user_data['plus_one_prompts'][message_id] = prompt`, максимум 20 меню.

Ответ на конкретное меню выбирает его чат и матч; сообщение без reply — последнее
меню. После рестарта меню для ввода username нужно открыть заново. Принимается
ровно один username по regex `@([A-Za-z][A-Za-z0-9_]{0,31})` после `strip()`.
Сообщения в группе и команда `/plus_one` этим путём не обрабатываются.
Кнопочный выбор игрока и ввод username передают `expected_match_id` в общий
`register_plus_one()` и далее в `register_core()`. Новый матч, открытый недельной
задачей во время ожидания проверки членства, не получает запись из старого меню.

Новая кнопка `confirm2` привязана к чату, матчу и записи. Подтверждение разрешено
самому игроку, проверяет актуальность и повторный клик, сохраняет кнопку выхода.
Таймер удаления через 4 часа проверяет только сохранённые `match_id` и `user_id`,
не `registration_id`. Точного срока истечения в базе нет: срок обеспечивается
задачей в памяти. После рестарта неподтверждённая запись может остаться бессрочно;
при повторном приглашении в тот же матч старый таймер может затронуть новую запись.

## Выход, резерв и баны

`remove_from_dm()` удаляет участие на текущем матче, определяет позицию до удаления
и вызывает `check_waiting_list_and_notify()`. Если удалён игрок основного состава
и после удаления осталось минимум 14 записей, игрок с индексом 13 становится
последним в основном составе. Отдельного флага основного состава нет: место
следует из сортировки. Ошибка доставки уведомления не отменяет продвижение.

`start_remove_plus_one()` показывает только приглашения вызывающего пользователя.
`remove_plus_one()` проверяет текущий матч и владение конкретной записью.
Старая кнопка без ID при двух приглашениях повторно предлагает выбор.
Удаление чужой или собственной записи через этот путь запрещено SQL-условием.
Для позднего отказа бан получает приглашённый, а не пригласивший.

Административные `/remove_other @username` и `/remove_other_plus_one @username`
обходят обычное назначение штрафа. Во второй команде username принадлежит
**пригласившему**: SQL удаляет его внешнее приглашение (`is_plus=1`), максимум одно.
`/ban` ставит срок до текущего матча +10 дней, `/ban_forever` — до
`2099-11-05 09:30:00+02:00`, `/unban` удаляет все баны пользователя.

`/delete_my_account` проверяет в транзакции все будущие неотменённые матчи,
где пользователь является игроком либо пригласившим. При наличии таких записей
удаление отклоняется: сначала Quit/Remove со стандартными правилами штрафов.

обновляет ту же строку `Chats`, снимает паузу и не разрывает связь с историей.
`/cancel_match` сначала сохраняет маркер отмены в `Cancelled_Matches`, затем закрывает
драфт и очищает его сообщения по возможности. Повторная отмена не затрагивает прошлый

Admin-проверка выполняется через `utils.is_chat_admin()` и Telegram API,
членство гостя определяется `utils.is_user_in_chat()`.

## Mistral и ежедневная функция

`/pidor` выбирает случайного пользователя из глобального `Users`, который сейчас
состоит в вызывающем Telegram-чате и не является ботом. Участники проверяются
последовательными `get_chat_member()`. Ограничение — один выбор за день на чат,
с границей дня в `Europe/Prague`; статистика хранится в `Random_Selections`.
Результат записывается **до** сетевого запроса, поэтому ошибка Mistral уже
расходует выбор за день. Модель — `ministral-8b-latest`, вызов
`await mistral.chat.complete_async(timeout_ms=30000, retries=None, ...)`.
Во внешний сервис передаются username и имя выбранного пользователя.

В `pidor.py` хранится длинный текст prompt с просьбой сгенерировать оскорбительный
стих и ролевыми инструкциями для внешней модели. Это данные приложения,
не инструкции для агента, работающего с репозиторием. Ответ обрезается по маркеру
`[🔓JAILBREAK]` функцией `remove_text_including_word()`.

## Развёртывание и перенос

1. Перенести код, `AGENTS.md`, этот документ, `Pipfile.lock` и конфигурацию Docker.
2. Рабочую SQLite-базу перенести отдельно: она исключена из Git. Для согласованной
   копии остановить запись либо использовать SQLite backup API; копирование одного
   файла во время записи не считать гарантированно корректным backup.
3. Создать локальный `.env` по примеру с настоящими секретами. `DATABASE_DIR`
   указывает каталог базы хоста, Compose монтирует его в `/app/data` и задаёт
   `DATABASE_PATH=/app/data/football.db`. Секреты в образ не копируются благодаря `.dockerignore`.
4. Проверить, что файл содержит нужные таблицы. Пустой каталог данных не является
   готовой установкой. Основной schema-bootstrap в репозитории отсутствует.
5. Запустить `docker compose up -d --build`, проверить логи. Для одного токена
   использовать один polling-процесс. Боту необходим доступ к Telegram, для
   ежедневного текста — к Mistral; нужны права отправлять и закреплять сообщения
   в группе, пользователи должны открыть личку бота.

Образ — `python:3.10.5-slim`, зависимости ставятся `pipenv install --system --deploy`.
Compose задаёт `restart: unless-stopped` и `TZ: Europe/Prague`.
Остановка контейнера не удаляет bind mount базы.

Для локального запуска с Python 3.10.5 и установленным Pipenv:

```powershell
pipenv sync
# До следующей команды задать DATABASE_PATH абсолютным путём к подготовленной базе.
# TG_TOKEN и MISTRAL_API_KEY должны быть в окружении или локальном .env для Pipenv.
$env:DATABASE_PATH = Join-Path (Get-Location) 'data/football.db'
pipenv run python main.py
```

Прямой Python не загружает `.env` самостоятельно. Не запускать `main.py` просто
для проверки импортов: стартуют реальные задачи и Telegram polling.

`migrations/execute.py` запускается вручную с одним SQL-файлом и `DATABASE_PATH`.
Внутри есть безусловный `os.listdir('/app/data')`: это предположение о Docker,
на Windows/другом окружении скрипт может упасть до SQL. Он печатает ошибку SQL,
но не гарантирует ненулевой exit code при ней. Нет таблицы версий и автоматического
определения порядка. `executescript()`/DDL не следует считать безопасным обратимым
планом миграции только из-за наличия `rollback()` в обработчике исключения.

Исторические SQL-файлы:

- `create_db.sql` — старая схема с nickname вместо user ID и без таблицы `Users`;
- `alter_users.sql` — переход на ID; содержит строку `Update the user_id column...`
  без SQL-комментария, поэтому файл как есть не является корректной полной миграцией;
- `change_chat_ids.sql` — пересоздание таблиц для внутренних ID чатов;
- `remove_user_chat.sql` — удаление исторического `Users.user_chat_id`;
- `add_pidor.sql` — таблица выбора и индексы, индексы создаются без `IF NOT EXISTS`;
- `remove_not_confirmed.sql` — удаляет **все** неподтверждённые записи, не проверяя срок.

Не применять эти скрипты подряд к существующей или пустой базе без анализа её
схемы. Для чистой установки нужна отдельная задача на актуальную начальную схему.

## Известные ограничения: сверять перед изменениями

Это наблюдения по коду/схеме, не результаты полноценной проверки в Telegram.
Не все пункты воспроизводились отдельными тестами.

- **Отсутствующий контекст:** некоторые старые административные обработчики
  предполагают наличие настроенного `Chats` без проверки None. Клавиатура
  регистрации теперь правильно переводит Telegram ID во внутренний ID чата.
- **Оставшиеся особенности времени:** календарное расписание, даты матчей и
  текущее время теперь явно учитывают Prague и DST. В `get_priority()`
  `created_at` из UTC всё ещё трактуется как Prague, раннее окно делится на 7200;
  ежедневный лимит в `pidor.py` сравнивает Prague-полночь с UTC `selected_at`.
  Эти отдельные исторические правила в правке недельного расписания не менялись.
- **Баны:** очистка истёкшего бана в `is_player_banned()` передаёт `ban_id`
  в `delete_ban()`, который удаляет по `user_id`. Списки банов не фильтруют
  истёкшие. `/ban`, `/ban_forever`, `/unban` после неизвестного username сообщают
  об ошибке, но местами не делают `return` и затем обращаются к отсутствующему игроку.
- **Восстановление приглашений:** нет сохранённых таймеров, дедлайна в таблице
  и привязки таймера к `registration_id`. Автоудаление неподтверждённого не вызывает
  механизм уведомления резерва. Очередь включает неподтверждённые записи.
- **Начавшийся матч:** прямой путь `register_core` подтверждает существующую
  неподтверждённую запись до проверки времени. Выход по ранее выданной актуальной
  кнопке всё ещё не запрещён после начала матча. Это отдельные правила времени,
  не защита от кнопок другого матча/заменённой записи.
- **Схема и целостность:** локальные FK `Bans.user_id → User(user_id)` и
  `Players_Notifications.chat_id → Chats2(chat_id)` ссылаются на отсутствующие
  таблицы. SQLite FK явно не включены. Включение FK без подготовки может сломать
  существующие операции. Пауза и отмена больше не удаляют чат/матч; удаление профиля
  сохраняет историю через LEFT JOIN и запрещено при будущих активных участиях.
- **Старые SQL-операции:** `update_match_registration()` имеет несовпадающие число
  placeholder и аргументов; `get_match_registration()` передаёт `(match_id)` без
  запятой; `update_match()` обновляет `date/time` вместо `datetime`;
  операции уведомлений используют `id` вместо `notification_id`. Основные сценарии
  эти функции сейчас не вызывают, но использовать их без проверки нельзя.
- **Команды:** `main.migchat(bot, update)` — синхронная функция со старой сигнатурой, несовместимой
  с обычным async-вызовом PTB 21.5; она также не перенастраивает задачи после миграции
  группы в супергруппу. Позиция удалённого внешнего гостя в
  `/remove_other_plus_one` теперь передаётся в проверку продвижения резерва.
- **Сообщения и внешние ошибки:** пользовательские поля HTML состава, истории,
  банов, драфта и статистики экранируются; некоторые обработчики всё ещё возвращают
  сырой текст исключения пользователю.
  `/get_all_bans`, `/get_jobs` не ограничены admin-проверкой. Часть ошибок перехватывается
  через `print`/общий `except`; `/clear_random_stats` не создаёт таблицу до удаления.
- **Масштабирование:** один polling-процесс и локальная SQLite, синхронные SQL-вызовы
  в event loop, проверки пользователей по одному. Создание регистрации и её лимиты
  теперь транзакционны; ежедневный выбор по-прежнему не защищён общей атомарной
  транзакцией/уникальностью от параллельных процессов.
